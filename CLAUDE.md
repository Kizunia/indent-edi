This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

All application code lives in `client/` (a Next.js app); the repo root only holds git metadata and the course documents (SRS, syllabus, project report). Run every command below from `client/`.

`client/AGENTS.md` (imported by `client/CLAUDE.md`, and regenerated by `next dev`) warns that this Next.js version (16.x, React 19) has breaking changes from what you may know, and says to read the guides in `node_modules/next/dist/docs/` before writing Next.js code. Run `npm install` first, since that directory only exists once dependencies are installed.

## Commands

The app needs a MySQL database (>= 8.0.16). First-time setup is in `client/prisma/README.md`; in short:

```bash
cp .env.example .env     # set DATABASE_URL=mysql://USER:PASSWORD@HOST:PORT/indent
npm install              # postinstall runs `prisma generate`
npm run db:migrate       # create tables (dev); use db:deploy on a server
npm run db:seed          # departments, types, items, stock, 2 demo indents (re-runnable)
npm run db:seed:sample   # optional: 20 more items, 16 indents covering every status
npm run dev              # http://localhost:3000, redirects / -> /indents
npm run build && npm run start
npm run lint             # eslint
npm run db:studio        # browse the data
```

Tests are integration tests against a real MySQL and are opt-in. Use a **separate** database whose name ends in `_test` (the migration must already be applied to it, e.g. `DATABASE_URL=.../indent_test npx prisma migrate deploy`):

```bash
TEST_DATABASE_URL="mysql://USER:PASS@HOST:PORT/indent_test" npm test
TEST_DATABASE_URL=... npx tsx --test --test-name-pattern="TC-11" tests/repositories.test.ts   # one test
```

Without `TEST_DATABASE_URL`, or if the database name does not end in `_test`, every test is skipped, so real data is never touched. The tests cover `lib/repositories/*` only (no UI or route-handler tests). `tsx` provides the `@/` path alias.

`npm run lint` currently reports 8 errors and 8 warnings in pre-existing UI/API files; `lib/`, `prisma/` and `tests/` are clean.

## What this is

"Organize Indent System": a purchase-indent (requisition) app built from an SRS. Users create an Indent (header plus line items), save it as Draft or Submit it, then search, filter, edit, delete, print, and export to Excel. `client/README.md` has the feature list and a table of the placeholder decisions (note: its storage sections still describe the old JSON files).

## Architecture

Four layers, with a deliberate seam at the repository layer:

1. **Pages** (`app/indents/**`, `"use client"`): `page.tsx` is the list, `new/page.tsx` the create form, `[id]/page.tsx` the detail/edit view. They fetch their own data from `/api/*` in `useEffect`; there are no server components or server actions doing data work. `app/page.tsx` redirects to `/indents`.
2. **Route handlers** (`app/api/**/route.ts`): thin wrappers that parse the request, call a repository, and return `{ error }` JSON on failure. Dynamic route `params` are a `Promise` and must be awaited.
3. **Repositories** (`lib/repositories/{indents,items,masters,stock}.ts`): the only code that touches Prisma, and where all business rules live. Plain async functions, so the data source can be swapped for an ERP later without touching routes or UI.
4. **Database** (`prisma/schema.prisma`, `migrations/0001_init`): 10 MySQL tables. `lib/db/` holds the plumbing: `client.ts` (Prisma singleton), `sequence.ts` (numbering), `mappers.ts` (DB rows <-> the UI contract in `lib/types.ts`), `dates.ts`, `errors.ts`.

### Things that are easy to miss

- **The UI contract is not the DB shape.** `lib/types.ts` uses string ids and display names (`department: "Stores"`); the database uses integer keys and foreign keys. Conversion lives only in `lib/db/mappers.ts`, and names are resolved back to rows in `repositories/masters.ts` (`requireDepartment`, `requireIndentType`, ...). An unknown department or type is rejected.
- **Error handling is deliberate.** Throw `AppError` for messages safe to show a user. Anything else is logged server-side and replaced with a generic message by `userMessage()` (FR-22), so raw Prisma/MySQL errors never reach the browser.
- **Numbers come from a counter table.** `nextSequence(tx, scope)` bumps a row in `number_sequence` inside the caller's transaction (row lock), so concurrent saves cannot get the same number and a rolled-back save rolls the counter back. Indent Numbers use one scope per day (`INDENT:YYYYMMDD` -> `IND-YYYYMMDD-####`); Item Codes use scope `ITEM` (`ITM-#####`).
- **Business rules are enforced on the server.** Status editability is data (`indent_status_master.is_editable`): only Draft is editable, so editing, removing an item, or changing the status of a Submitted Indent is rejected by the repository, not just hidden on screen. **Gap:** `deleteIndent` has no status check, so a Submitted Indent can still be deleted by calling the API directly; only the detail page hides the button. An Indent must keep at least one item (the delete is rolled back otherwise). Quantity must be > 0 (also a DB CHECK).
- **Snapshots.** Indent lines copy the item's code, name, specification, drawing number and the stock seen at entry into `*_snapshot` columns, taken from the catalogue on the server, not from the client. Creating an Indent never writes stock (BR-04).
- **Soft delete and history.** `deleteIndent` sets `deleted_at` (the row and its number stay); every query filters `deletedAt: null`. Status changes append to `indent_status_history`. `version` supports optimistic locking, but only when the client sends `version` (the UI currently does not).
- **Statuses.** The migration inserts only Draft and Submitted. Pending Approval, Approved, Rejected and Cancelled exist only after `db:seed:sample` and are placeholders from the SRS; the list screen's status filter hard-codes all six.
- `createdBy` is a typed name used as both user id and display name; there is no authentication or permission check (SRS leaves both to other modules).
- `data/*.json` is no longer read at runtime. It is only the input for `prisma/seed.ts`.
- `app/api/indents/export/route.ts` builds the `.xlsx` with the `xlsx` package: mode `selected` (by `ids`) or `all` (re-applies the list filters with a huge page size), one row per indent item.
- Printing uses the browser print dialog with `@media print` rules in `app/globals.css` (`.no-print`, `.print-area`). Styling is Tailwind v4; imports use the `@/` alias for the `client/` root.

### SRS placeholders

The SRS leaves many decisions as TBD (number formats, status list, search semantics, editable fields, roles, ...). Each placeholder is marked in code with a comment citing the SRS section. `grep -rn TBD client/lib client/app client/components client/prisma` finds them. When one is replaced, update the comment and the README table together.
