## What this is

"Organize Indent System": a purchase-indent (requisition) app built from an SRS. Users create an Indent (header plus line items), save it as Draft or Submit it, then search, filter, edit, delete, print, and export to Excel. `client/README.md` has the feature list and a table of the placeholder decisions.

## Architecture

Three layers, with a deliberate seam at the data layer:

1. **Pages** (`app/indents/**`, `"use client"`): `page.tsx` is the list, `new/page.tsx` the create form, `[id]/page.tsx` the detail/edit view. They fetch their own data from `/api/*` in `useEffect`, so there are no server components or server actions doing data work. `app/page.tsx` just redirects to `/indents`.
2. **Route handlers** (`app/api/**/route.ts`): thin wrappers that parse the request, call `lib/store.ts`, and return `{ error }` JSON with a 400 on exceptions. The UI shows those messages directly. Dynamic route `params` are a `Promise` and must be awaited.
3. **Data layer** (`lib/store.ts`): the only code that touches storage. It reads and writes flat JSON files in `client/data/` with synchronous `fs` calls, resolved via `process.cwd()`, so the server must be started from `client/`. Each call re-reads the whole file and writes it back in full, so there is no locking or concurrency safety. `lib/types.ts` holds the domain types (`Indent`, `IndentItem`, `Item`, `StockRecord`, ...).

`lib/store.ts` is intended to be swapped for a real database or ERP integration later. Keep its function signatures stable, and put new storage logic there rather than in route handlers or components.

### Things that are easy to miss

- `data/*.json` is tracked in git and mutated at runtime. Using the app (creating indents or items) dirties the working tree, so don't commit incidental data changes by accident.
- An `Indent` embeds its `items` (`IndentItem[]`). Each line item snapshots the item's name, code and stock at entry time (`currentStockAtEntry`), and does not reference the live master. Creating a new `Item` also appends a zero-quantity row to `stock.json`.
- Business rules in the store: an Indent must always have at least one item (enforced in `createIndent`, `deleteIndentItem`, and the POST handler). `updateIndent` only patches `remark`, `status`, and the item fields `purpose`, `requiredQuantity`, `requiredDate`, `unit`. Everything else is immutable.
- The README says edit and delete are allowed only in Draft status, but `lib/store.ts` doesn't check status. Any such restriction currently lives in the UI only.
- `app/api/indents/export/route.ts` builds the `.xlsx` with the `xlsx` package. It has two modes: `selected` (by `ids`) and `all`, where `all` re-applies the list filters via `queryIndents` with a huge `pageSize`. It emits one row per indent item.
- Printing uses the browser print dialog with `@media print` rules in `app/globals.css` (`.no-print`, `.print-area`). Mark non-printing UI with `no-print`.
- Styling is Tailwind v4 (`@tailwindcss/postcss`). Imports use the `@/` alias for the `client/` root.

### SRS placeholders

The SRS leaves many decisions as TBD (Indent Number format `IND-YYYYMMDD-####`, Item Code `ITM-#####`, status list, search semantics, editable fields, no auth or roles, ...). Each placeholder is marked in code with a comment citing the SRS section. `grep -rn TBD client/lib client/app client/components` finds them. When a placeholder is replaced, update the comment and the README table together.
